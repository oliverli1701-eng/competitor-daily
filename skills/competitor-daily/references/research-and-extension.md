# 检索、核验与扩展

## 官方来源

先从赛事官网、主办方通知和官方附件建立来源注册表，再逐个查找该届赛事。使用 `sources --help` 查阅本版命令。来源配置应限制到对应官方域名，校内选拔通知的适用对象与全国比赛资格要分开记录。

名单导入是“有哪些赛事需要关注”，来源注册是“从哪里核验”，日报状态是“本届赛事发生了什么”。三者分别维护，避免换一份名单就需要修改模板。

## 使用 Agent 自己的检索能力

运行 `run --help` 查看 `--from-research` 的目录参数。复制 [research-template.json](research-template.json) 到用户 workspace 的研究目录，命名为 `batch_01.json`，用真实核验结果替换模板内容；不要把模板当作真实赛事。`as_of` 是日报日期 `YYYY-MM-DD`，必须与 `run --date` 日期一致。事件结构由 `validate_event` 校验。所有已确认名单编号都要有 coverage，只有实际打开并核验了匹配通知才写 `verified_event`；已读官方正文没有当届通知写 `no_current_notice`，无法完成写 `failed` 或 `inconclusive`，不能把检索失败写成没有通知。

```text
python scripts/competitor_daily.py --root /path/to/my-daily run --from-research /path/to/my-daily/research --date 2026-10-20
```

记录 `sources` 的真实 URL、标题和通知发布日期；没有日期不要补猜。`evidence` 可记录 `{ "field": "registration_end", "url": "官方URL", "quote": "原文逐字摘录的截止日期句子" }`。Agent 模式由调用它的 Agent 对原文负责，程序执行结构、时态、覆盖与状态校验；直接 API 模式另有自动逐字证据校验。`demo` 仅生成虚构版式预览，不创建真实检索批次或历史快照。

每条有效事实需能追溯到已打开的官方页面或附件。对于不同赛道、届次、报名轮次分别记录标识；原文没有确认的“取消”“延期”“报名截止”不能根据页面沉默推断。检索结果中的短摘要不能替代原文核验。

这种模式由用户正在使用的 Agent 负责检索、提取和归档证据，再由本地程序校验、比较状态、渲染；它不是与任何 Agent 供应商之间的内置 API 集成，也不意味着免费。

## 扩展界面

- 文档输入：在导入层增加解析器，输出同一个待确认目录结构；不要把 OCR 或模型调用藏进纯本地导入命令。
- 检索提供方：在网络层适配搜索/模型接口，保留官方来源和事实核验，再交给原有状态合并与发布流程。
- 大学与视觉品牌：使用 workspace 的 `config/profile.json`，模板从同一份品牌配置读取，避免硬编码学校。
- 新字段或栏目：先扩展事件结构与验证逻辑，再同步 HTML、PDF 和演示数据；不以新增模板文案伪造数据能力。

升级程序不应覆盖用户 workspace。用 demo、一个小范围正式来源和现有测试核验变化后，再处理完整名单。
